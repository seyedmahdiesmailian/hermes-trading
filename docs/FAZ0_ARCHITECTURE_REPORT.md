## ۱. خلاصه اجرایی

سیستم در حال حاضر **کار می‌کند** — واقعاً ترید می‌کند، واقعاً پول واقعی روی حساب دمو اجرا می‌کند.
اما **نمی‌تواند سودده باشد**، نه به خاطر تحلیل اشتباه، بلکه به خاطر یک **نقص ساختاری در مدیریت ریسک**.

اعداد کلیدی (۲۱ روز، ۵۴ معامله بسته‌شده):

| شاخص | مقدار |
|---|---|
| بالانس شروع | ۵۰۳۶٫۷۵ دلار |
| بالانس نهایی | ۵۱۰۴٫۴۷ دلار |
| سود خالص | **+۶۷٫۷۲ دلار** |
| وین‌ریت | **۶۹٪** (۳۷ از ۵۴) |
| متوسط سود روزانه | +۳٫۲۲ دلار |
| حداکثر دراو‌داون | ۲۸۴ دلار (۵٫۶٪) |
| تعداد معاملات در روز | ۲٫۶ |

**۶۹٪ وین‌ریت عالی است. سود ۶۷ دلار در ۳ هفته فاجعه است.**

### ۲.۳ پنج معامله‌ی مرگ

پنج معامله وجود دارد که **هر کدام ۲٪ از کل حساب** ضرر داده‌اند،
در حالی که خط‌مشی، ریسک مجاز را **۱٫۵٪** تعیین کرده است:

| تاریخ | ضرر | درصد از حساب | حجم |
|---|---|---|---|
| ۰۹-۰۳ | -۱۰۲٫۸۸ | ۲٫۰٪ | ۰٫۱۶ |
| ۰۹-۰۷ | -۹۹٫۲۸ | ۲٫۰٪ | ۰٫۱۷ |
| ۰۹-۰۸ | -۸۹٫۱۰ | ۱٫۸٪ | ۰٫۰۶ |
| ۰۹-۰۹ | -۹۵٫۱۰ | ۱٫۹٪ | ۰٫۱۵ |
| ۰۹-۱۷ | -۹۹٫۷۲ | ۲٫۰٪ | ۰٫۰۳ |

مجموع این ۵ معامله: **-۴۸۶ دلار**، یعنی **۷ برابر کل سود خالص سیستم.**

نکته بسیار مهم: این پنج معامله **همگی پس از اصلاح b196 (۰۹-۰۹)** هم رخ داده‌اند (دو مورد).
یعنی اصلاح «base_risk_pct خوانده شود» اجرا شده، اما **سقف هنوز ۲٪ است**.

### ۲.۴ ریشه در کد

```python
# engines/auto_executor.py:21
MAX_RISK_PER_TRADE_PCT = 0.02       # 2% of balance per trade

# engines/risk.py:4-11  (خط‌مشی)
def _base_risk_pct(balance):
    if balance < 800:   return 0.01
    if balance < 1500:  return 0.015
    if balance < 5000:  return 0.02
    return 0.015          # ← بالانس ما ۵۰۳۶ است، اینجا می‌خورد
```

و در `build_proposal`:

```python
# engines/auto_executor.py:368
base_pct = min(_policy_base, MAX_RISK_PER_TRADE_PCT) if _policy_base > 0 \
    else MAX_RISK_PER_TRADE_PCT
```

با بالانس ۵۰۳۶:
- `_policy_base` = ۰٫۰۱۵ (درست)
- `MAX_RISK_PER_TRADE_PCT` = ۰٫۰۲ (خط‌مشی می‌گوید ۱٫۵٪، ثابت کد ۲٪)
- `base_pct = min(0.015, 0.02) = 0.015` ← **در این مسیر درست است**

پس چرا ۲٪ ضرر داده شده؟ چون **اینها قبل از b196** نبوده‌اند.
دو مورد پس از b196 رخ داده — یعنی مسیر دیگری هم وجود دارد که ریسک را می‌شکند.

**دو مظنون اصلی:**

۱. **`risk_mult` تطبیقی** (خط ۳۷۰): `risk_pct = base_pct * risk_mult`
   اگر `risk_mult` به جای ≤۱٫۰، مقدار >۱ بگیرد، ریسک از سقف بالا می‌رود.
   کد فرض می‌کند `risk_mult ≤ ۱٫۰` اما **هیچ `clamp`ی وجود ندارد**.

۲. **حساب مالیه/سواپ**: در ژورنال، ستون‌های `commission` و `swap` وجود دارند
   اما در محاسبه P&Lِ تصمیم‌گیری **به کار گرفته نمی‌شوند**.
   کارمزد واقعی هر معامله در ستون `commission` دیده می‌شود (مثلاً -۰٫۱۲ تا -۰٫۱۶)
   که در ضررهای «۲٪» حساب نشده.

## ۴. ممیزی سیستماتیک — مشکلات طبقه‌بندی‌شده

### ۴.۱ بحرانی (C) — مستقیماً روی پول اثر دارد

**C1 — ریسک ۲٪ به جای ۱٫۵٪**
پنج معامله ۴۸۶ دلار ضرر فراتر از خط‌مشی. سقف کد `MAX_RISK_PER_TRADE_PCT=0.02`
در حالی که خط‌مشی بالانس >۵۰۰۰ را ۱٫۵٪ تعیین می‌کند.
*راه حل:* سقف از خط‌مشی خوانده شود، ثابت ۲٪ حذف شود.

**C2 — `risk_mult` بدون clamp**
خط ۳۷۰ `auto_executor.py`: `risk_pct = base_pct * risk_mult`.
فرض می‌شود ≤۱٫۰ باشد اما **هیچ محدودیتی وجود ندارد**.
اگر learning-state مقدار >۱ تولید کند، ریسک از سقف بالا می‌رود.
*راه حل:* `risk_pct = min(base_pct * mult, MAX)` با clamp صریح.

**C3 — کارمزد و سواپ در تصمیم‌گیری لحاظ نمی‌شود**
ژورنال ستون‌های `commission`/`swap` دارد اما sizing فقط `stop_distance` را می‌بیند.
هر معامله ۰٫۱۲–۰٫۱۶ دلار کارمزد دارد که در RR حساب نشده.
*راه حل:* کارمزد تخمینی به هزینه ترید اضافه شود.

**C4 — اسلایسینگ نامتقارن برنده/بازنده**
بازندها ۲ برابر برندها حجم دارند (۰٫۰۶۰ در برابر ۰٫۰۳۴).
ریشه: `stop_distance` متغیر است (`sl = plan["invalidation"]` ثابت است،
پس وقتی قیمت میرود، فاصله استاپ بزرگ می‌شود و lot هم بزرگ).
*راه حل:* فاصله استاپ با ATR محدود شود (`stop_dist_cap`).

### ۴.۲ ساختاری (S) — معماری را تضعیف می‌کند

**S1 — `stop_distance = |entry - sl|` با `sl = plan["invalidation"]`**
`invalidation` یک قیمت ساختاری است (~۸۰ دلار دورتر در پلن فعلی).
این در نگاه اول منطقی است، اما باعث می‌شود risk-per-trade وابسته به
جابجایی قیمت باشد، نه به نوسان واقعی بازار.
*راه حل:* استاپ با ATR ساخته شود، invalidation فقط به‌عنوان fallback.

**S2 — حجم عظیم `scripts/` بدون مرز مشخص**
۱۷۵ اسکریپت تحقیقاتی در کنار کد تولید. پروب‌ها ledgers خودشان را
در `data/backtest/` پین می‌کنند که باعث وابستگی متقابل می‌شود.
*راه حل:* `archive/` (که ساخته شد) + مرز صریح در DEPLOY.md.

**S3 — race condition بین autopilot و suite تست**
autopilot زنده وسط اجرای suite کامل، ledgers را دوباره می‌نویسد و commit می‌کند.
۴ تا ۲۴ تست به صورت تصادفی شکست می‌خورند.
*راه حل:* lock دور re-derive ledgers یا کپی ledgers به scratch dir قبل از suite.

**S4 — دو منبع حقیقت برای Python**
system Python 3.12 (دایمون‌ها) در برابر `.venv` 3.14 (cron).
این باعث شده بود cron از ۲۰۲۶-۰۹-۲۰ به مدت ۱۱ روز بشکند.
*راه حل:* تک‌منبعی شدن وابستگی‌ها (`requirements.txt` + ساختار واحد).

## ۵. معماری هدف (پاسخ به سوالات مرحله دوم)

### ۵.۱ آیا ساختار فعلی مناسب ربات حرفه‌ای است؟

**بخش منطق تجاری: بله.** `engines/` به خوبی فکتور شده است:
`context.py` (تحلیل)، `plan.py` (برنامه)، `risk.py` (خط‌مشی)،
`auto_executor.py` (اجرا)، `trade_management.py` (مدیریت).
هر کدام وظیفه واحدی دارد و از بقیه جدا است.

**بخش مدیریت ریسک: نه.** همانطور که در بخش ۴ دیدیم، چندین مسیر
وجود دارد که می‌توانند ریسک را از خط‌مشی خارج کنند بدون اینکه
کسی جلویشان را بگیرد. **این نقطه‌ای است که باید بازطراحی شود.**

**بخش زیرساخت: قابل توسعه است.** systemd + HTTP bridge + SQLite
برای مقیاس فعلی کافی است. Bridge با Bearer auth روی LAN امن است.

### ۵.۲ پاسخ به سوالات مشخص

| سوال | پاسخ |
|---|---|
| آیا قابلیت توسعه دارد؟ | **بله** — فکتورینگ `engines/` سالم است |
| آیا مقیاس‌پذیر است؟ | **بله** برای یک نماد؛ برای چند نماد به key-per-symbol نیاز است |
| آیا برای اتصال به متاتریدر مناسب است؟ | **بله** — bridge فعلی کار می‌کند (HTTP + Bearer) |
| چه بخش‌هایی باید بازطراحی شوند؟ | **مدیریت ریسک** (C1–C4) — همه‌چیز در یک لایه متمرکز |
| چه تکنولوژی‌هایی باید اضافه شوند؟ | قفل فایل دور ledgers، حساب کارمزد، ATR-bounded stops |

### ۵.۳ معماری پیشنهادی لایه ریسک

ایده اصلی: **یک تابع واحد `size_and_validate()` که تنها نقطه تولید دستور است.**

```
proposal ──→ ┌─────────────────────────────────────────┐
             │  engines/risk.py  (نقش واحد)             │
             │                                          │
             │  1. risk_budget = balance * policy(bal)  │  ← خط‌مشی، نه ثابت کد
             │  2. stop = ATR-bounded(plan.invalid)     │  ← S1/C4
             │  3. cost = commission + swap estimate    │  ← C3
             │  4. lot = budget / (stop + cost)         │
             │  5. clamp(risk_pct, 0, POLICY_MAX)       │  ← C1/C2
             │  6. assert(lot * stop * 100 <= budget)   │  ← در صورت نقض رد کن
             └─────────────────────────────────────────┘
                          │
                          ▼
                    bridge_client.execute()
```

این لایه **هیچ ورودی از بیرون نمی‌گیرد** — همه‌چیز از خط‌مشی محاسبه می‌شود.
اگر چیزی نقض شود، ترید رد می‌شود، نه اینکه با حجم بزرگتر اجرا شود.

طبق قانون پروژه («قبل از اجرای هر تغییر بزرگ، ابتدا تحلیل، مزایا،
معایب و ریسک‌ها را توضیح بده و تایید بگیر»):

**آیا با شروع فاز یک (اقدام ۱) موافقی؟**

مزایا:
- جلوگیری از ۴۸۶ دلار ضرر فراتر از خط‌مشی در ۵ معامله مشابه
- تغییر tighten-only: هیچ ترید قابل‌اجرا‌یی که امروز اجرا می‌شود رد نمی‌شود
- یک commit مستقل با تست قفل‌کننده

معایب:
- اگر بالانس زیر ۵۰۰۰ برود، ریسک به ۲٪ برمی‌گردد (طبق خط‌مشی، درست است)
- نیاز به re-derive ledgers که بر پروب‌ها اثر می‌گذارد

ریسک:
- کم. مسیر بحرانی پوشش داده شده با ۱۹۲۶ تست سبز.
