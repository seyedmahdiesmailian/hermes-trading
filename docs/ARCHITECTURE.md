# معماری هرمس — از نقطه صفر

> سند مرجع طراحی. تا تایید کاربر، کدی نوشته نمی‌شود.

---

## ۱. اصل طراحی

**یک پروسه، یک حلقه، یک حقیقت.**

- **یک پروسه:** همه کارها را یک دیمن انجام می‌دهد (نه ۸ سرویس).
- **یک حلقه:** همان حلقه‌ای که ورود را تصمیم می‌گیرد، مدیریت خروج را هم انجام می‌دهد.
- **یک حقیقت:** وضعیت حساب و پوزیشن‌ها **فقط از خود بروکر (MT5bridge)** خوانده می‌شود. دیتابیس فقط **دفتر کل** است (audit + بک‌تست)، هرگز منبع تصمیم.

این سه اصل، ریشه‌ای‌ترین باگی که الان موجود است را می‌کشد: دیمن مدیریت پوزیشن امروز از SQLite می‌خواند که هیچ‌کس در آن نمی‌نویسد — پس **برای همیشه ۰ پوزیشن** می‌بیند و دروازه `MAX_OPEN_POSITIONS` کور است. در معماری جدید، پرسش از بروکر زنده‌است یا اصلاً ترید نمی‌کنیم (fail-closed).

## ۲. ساختار فایل (۱۲ فایل، نه بیشتر)

```
hermes-trading/
├── .env                    # رمزها (همان، دست‌نخورده)
├── config.yaml             # پارامترهای ترید (یک جا، نه پخش در کد)
├── hermes.db               # دیتابیس واحد
│
├── core/                   # مغز — هیچ وابستگی به MT5/تلگرام ندارد
│   ├── entities.py         # Plan / Order / Position / Signal / AccountState + Enumها
│   ├── gates.py            # ExecutionGuard — دروازه‌های fail-closed
│   ├── engine.py           # تحلیل + تصمیم + ریسک
│   ├── db.py               # لایه SQLite (دفتر کل)
│   └── params.py           # خواندن config.yaml + مدیریت knobs یادگیری
│
├── adapters/               # دست‌ها (بیرون از مغز)
│   ├── mt5.py              # bridge HTTP client (داده بازار + اجرای سفارش)
│   ├── signals.py          # خواندن JSON فوروارددر تلگرام
│   └── notify.py           # گزارش تلگرامی به کاربر
│
├── entry/
│   ├── hermes.py           # دیمن اصلی — تنها پروسه زنده
│   └── backtest.py         # بک‌تستر آفلاین روی کندل‌های تاریخی
│
└── tests/
```

**زنجیره وابستگی یک‌طرفه است و هیچ‌وقت برعکس نمی‌شود:**
`entry → core → adapters` — idiot-proof. `core` هرگز `adapters` را import نمی‌کند.

## ۳. حلقه اصلی (`entry/hermes.py`)

دیمن واحد با دو تایمر درون یک پروسه:

### تایمر ورود — هر ۵ دقیقه
1. bridge: کندل‌ها + تیک فعلی XAUUSD
2. bridge: وضعیت حساب **و پوزیشن‌های باز** (زنده، بدون cache)
3. signals: آیا سیگنال جدیدی از کانال رسیده؟ (با offset ذخیره‌شده)
4. engine: تحلیل بازار → تصمیم (ورود / انتظار)
5. در صورت ورود:
   - **gates.evaluate()** → ممنوع؟ → ثبت در `guard_log` + گزارش، پایان
   - مجاز؟ → `mt5.place_order()` → نتیجه در `orders` + `trades`
6. گزارش کوتاه تلگرامی

### تایمر مدیریت — هر ۱۵ ثانیه
1. bridge: پوزیشن‌های باز (زنده)
2. برای هر پوزیشن: trailing stop / breakeven / خروج اضطراری
3. در صورت خروج: `mt5.close_position()` → بستن رکورد در `trades` + گزارش

> ۱۵ ثانیه برای طلا کافی است. ما HFT نیستیم. این ساده‌سازی، یک پروسه را ممکن می‌کند.

## ۴. مدل داده (`hermes.db`)

| جدول | نقش |
|---|---|
| `plans` | برنامه ورود (symbol/dir/entry/sl/tp/size/grade/style/source) |
| `orders` | سفارش‌های ثبت‌شده + ticket بروکر |
| `trades` | معاملات بسته‌شده + pnl + exit_reason (خوراک بک‌تست) |
| `signals` | سیگنال خام کانال + parse + وضعیت پردازش |
| `equity_snapshots` | موجودی/اکوییتی در هر سیکل |
| `guard_log` | **هر** تصمیم دروازه (مجاز/ممنوع + reasons) — شفافیت کامل |
| `params` | knobs یادگیری + state (مثل lastSignalId) |

هیچ جدول تکراری، هیچ schema drift. `NOT NULL`ها با مقدار واقعی از همان روز اول.

## ۵. دروازه‌های امنیت (`core/gates.py`)

منتقل از `ExecutionGuard` موجود (۷۷/۷۷ تست سبز — دارایی اثبات‌شده):

- ۱ پوزیشن همزمان، حداکثر ۵ ترید روزانه
- حداکثر ۲٪ ریسک هر معامله، ۵٪ ضرر روزانه = توقف
- حداقل RR = ۱.۰ (با exempt برای استایل‌های قوی)
- حداقل گرید B، حداقل فاصله استاپ (ATR × ۲)
- **قانون طلایی (b29):** هر خطای دروازه جلوی ورود را می‌گیرد، هرگز راه نمی‌دهد.

**تضمین معماری:** `mt5.place_order()` تنها در `entry/hermes.py` و **فقط** بعد از `gates.evaluate()` فراخوانی می‌شود. مسیر دیگری وجود ندارد — در فیزیک کد غیرممکن است.

---

## ۶. یادگیری (`core/params.py`)

- knobs (min_rr، min_grade، risk_mult) در جدول `params`
- فقط از معاملات **بسته‌شده واقعی** به‌روزرسانی می‌شوند
- **فقط سخت‌تر می‌شوند، هرگز نرم‌تر** (fail-closed)
- هر تغییر در `guard_log` ثبت می‌شود

## ۷. چه چیزی از سیستم قبل باز استفاده می‌شود

| دارایی | وضعیت |
|---|---|
| MT5 Bridge روی ویندوز | ✅ سالم و در حال کار ($۴,۹۳۲ دمو، API کامل) |
| ثابت‌های دروازه V1 | ✅ اثرگذاشته در ExecutionGuard، ۷۷/۷۷ تست |
| ۶۲ معامله تاریخچه | ✅ به‌عنوان seed بک‌تست |
| فوروارددر سیگنال تلگرام | ✅ سالم، JSON می‌دهد |
| کد فعلی V2 (use cases، JSON repos) | ❌ کنار گذاشته شد — استب کامل، دست‌نیاز به وصله |

## ۸. ریسک‌ها و مقابلہ

| ریسک | مقابلہ |
|---|---|
| یک پروسه = یک نقطه شکست | systemd `Restart=always` + watchdog ساده |
| Bridge (ویندوز) نقطه شکست | fail-closed: bridge نرسد = ترید نمی‌کنیم |
| یادگیری اشتباه ریسک را بالا ببرد | قانون فقط-سخت‌تر + لاگ کامل |
| بک‌تست با تنظیمات غلط | ثابت‌ها import شوند، نه literal (قانون skill) |

## ۹. فازهای ساخت (همه DRY_RUN تا بک‌تست سبز)

- **فاز A:** `core/entities` + `core/db` + `adapters/mt5` — خواندن بازار/حساب و دفتر کل
- **فاز B:** `core/engine` + `core/gates` — تصمیم و دروازه
- **فاز C:** `entry/hermes` — دیمن واحد، DRY_RUN
- **فاز D:** `entry/backtest` — اعتبارسنجی روی تاریخچه
- **فاز E:** بک‌تست سبز → DRY_RUN=False → لایو

هر فاز: تست + کامی‌ت. بدون پرسش، بدون ورود دستی.
